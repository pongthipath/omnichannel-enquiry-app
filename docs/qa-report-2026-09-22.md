# QA Report — Omnichannel Enquiry System — 2026-09-22

Scope: local dev environment QA in response to "ใช้งานไม่ได้เลย" (doesn't work at all).
Method: environment/service checks, unit tests, `tsc`/lint, `expo export --platform web`,
direct API testing via curl (auth, scope, status transitions, idempotency, offline sync),
and real end-to-end browser testing via headless Chrome driven over the DevTools Protocol
(actual login/logout/reload against the running app at :8081 and API at :4000, with
console/network/exception capture — not just code reading).

**Bottom line: the app does not "not work at all."** Login, session persistence across
reload, logout, and the enquiry list all work correctly end-to-end against the real API,
with zero console errors/exceptions and zero unexpected network failures in every scenario
tested. What's true is that the built UI is very thin (list-only, from the stated scope) and
**has one real UI bug** (dead-end tap target) plus **large missing surface vs. the ux-ui/design
docs and the brief** (no chat, no create-enquiry, no staff actions) — that is almost certainly
why it "feels" broken to a user expecting a working enquiry+chat app.

## End-to-end browser test results (headless Chrome via CDP, real network calls to :4000)

All of the following were driven against the actually-running app/API, not simulated:

1. **Login (customer, demo account "Bangkok Bistro")**: click demo button → fills fields →
   submit → navigates to `/enquiries` → list renders real data from the API. **0 console
   errors, 0 exceptions, 0 unexpected network errors.**
2. **Wrong password**: shows `"อีเมลหรือรหัสผ่านไม่ถูกต้อง"` (auth.invalidCredentials) plus the
   correct "you're on the Customer tab" hint, exactly as designed in `login.tsx`. Works.
3. **Hard reload while logged in** (`Page.reload(ignoreCache)`): access token (in-memory)
   is lost as expected, first `/auth/me` call gets a `401`, the app's 401-handler
   (`http-client.ts` → `setUnauthorizedHandler`) silently calls `/auth/refresh` with the
   refresh token from `localStorage`, retries, and the user stays on `/enquiries` with data
   intact. No visible glitch, no re-login prompt. **Works correctly** (note: `session.restore`
   in `session.ts` is exported but never called anywhere in the app — dead code; not a bug
   because the lazy 401-refresh path already covers the reload case).
4. **Logout**: clears `localStorage` (`omni.refreshToken` removed), redirects to `/login`,
   fires `POST /auth/logout` (204). Works.

## Bugs

### BUG-1 (major) — Enquiry list cards are dead: tapping does nothing, no way to open a chat
- **Steps to reproduce**: Log in as any customer or staff → on `/enquiries`, tap/click any
  enquiry card.
- **Expected**: Per `ux-ui.md` line 32, `[C1 รายการ] → แตะการ์ด → [C4 thread]` — tapping a card
  must open the enquiry thread/detail.
- **Actual**: The `Card` in `renderItem` has no `onPress`/`Pressable` wrapper at all — it's
  static `View`s and `Text`. Tapping is a complete no-op. Confirmed by reading the component
  and by the live CDP test (no navigation, no route change on click).
- **Suspected file:line**: `omnichannel-enquiry-app/src/app/(app)/enquiries.tsx:19-53`
  (`renderItem` — `<Card className="gap-2 p-4">` never receives a press handler).
- **Spec violated**: `ux-ui.md` §C1 (line 32, flow `C1 → แตะการ์ด → C4`).
- **Note**: this is the single most likely reason a real user says "it doesn't work at all" —
  the list is the *only* screen with content, and every row looks tappable (card, shadow,
  chevron-less list item) but does nothing.

### BUG-2 (minor) — `npm run seed:demo -- --clean` silently ignores `--clean` on this Windows/npm setup
- **Steps to reproduce**: In the API repo, run `npm run seed:demo -- --clean`.
- **Expected**: Prints `--clean: removed N non-demo chats` and deletes any non-demo chat rows
  (per the script's own doc comment, `demo-seed.ts:8`).
- **Actual**: Runs successfully but the `--clean` flag never reaches `process.argv` — the
  clean branch is silently skipped (no error, no log line, stale test data from earlier API
  calls stayed in the DB). Verified reproducible: `npm run seed:demo -- --clean` → no
  "removed" line and non-demo chats stayed; `npx ts-node src/database/seeds/demo-seed.ts
  --clean` (bypassing the npm script) → correctly printed `--clean: removed 3 non-demo chats`
  and deleted them.
- **Suspected cause**: npm's `--` argument-forwarding through the Windows npm.ps1/npm.cmd
  shim in this environment, not the script itself (`demo-seed.ts:13`,
  `const clean = process.argv.includes('--clean')`, is correct in isolation).
- **Impact**: Low — dev/QA tooling only, doesn't affect the running app — but worth knowing:
  on Windows, use `npx ts-node src/database/seeds/demo-seed.ts --clean` directly instead of
  the `npm run` wrapper if you need a guaranteed clean.
- **Spec violated**: none (tooling, not app behavior) — filed as a bug because it's silently
  wrong (no error, wrong result) rather than an intentional gap.

### Minor inconsistencies (not filed as bugs — no spec violated / no functional impact)
- `design.md` line 749 describes idempotent create as `header Idempotency-Key`; the actual
  implementation uses a body field `clientRequestId` (`enquiry.dto.ts:19-26`). Behavior is
  correct and well-tested (verified below); the design doc's wording is just stale.
- `http-client.ts:43` comment says `// web: httpOnly refresh cookie`, but the API never sets
  a cookie (`Set-Cookie` absent from `/auth/login` response) and the app actually stores the
  refresh token in `localStorage` (`session-store.ts:9`, itself correctly documented as "for
  now"). `credentials: 'include'` is harmless dead configuration, not a bug.
- Swagger JSON (`/api/docs-json`) has mojibake in `SyncItemDto.payload.description`
  (`"conversation.create â†’ ..."`) — a UTF-8 arrow character mis-encoded in the source
  `@ApiPropertyOptional` string. Cosmetic, Swagger UI only.

## Missing vs. brief (not bugs — not built yet), ranked by what blocks a demo

1. **No enquiry detail / chat thread screen (C4)** — biggest gap. Can't read/send messages,
   can't see the timeline/delivery-state UX described in `ux-ui.md`. Combined with BUG-1
   (dead tap target), this is what makes the app look non-functional to a real user.
2. **No create-enquiry screen (C3)** — customers can't file a new enquiry from the app (API
   supports it and is fully tested/working, per above).
3. **No staff actions in the UI** — no assign/take, no status change buttons, no escalate,
   no internal notes, no Customer Panel — all present and correct in the API, none wired to
   any screen.
4. **No realtime** — `socket.io-client` is not referenced anywhere in the app; the
   `RealtimeGateway` on the API side is untested by this pass (no UI consumes it).
5. **No pagination on the list** — `FlatList` has no `onEndReached`; `nextCursor` from the API
   is fetched but unused, so lists beyond `limit=30` are unreachable from the UI.
6. **No offline queue in the UI** — `POST /messages/sync` works and is idempotent on the API
   side (verified above), but nothing in the app currently calls it.
7. Login screen text mismatch: `common.json` `auth.login.staffTitle` key exists but is unused
   (screen always shows `auth.login.title` "Sign in" for both tabs, only the subtitle changes)
   — cosmetic, not filed as a bug since no spec explicitly requires a different title per tab.

## Recommendation
Not a "backend is broken" situation — the API is solid (44/44 tests, every scope/status/
idempotency/authz check above passed). Before the next demo:
1. Fix BUG-1 (wire `onPress` on the enquiry card to navigate somewhere, even a stub) so the
   app doesn't feel dead on the only screen that has content.
2. Prioritize the C4 chat thread screen — without it the "omnichannel enquiry" premise isn't
   demonstrable at all, regardless of how correct the API is.
3. BUG-2 is a nice-to-have fix for local dev hygiene, not release-blocking.
